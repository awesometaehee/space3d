# 에이전트 구조 (AG-UI)

## 한눈에 보기

```
┌──────────────── 화면 (React) ────────────────┐
│ 하단 입력창 ─┐                                │
│ 오른쪽 패널 ←┼─ useAgent ← AG-UI 이벤트 스트림 │
│   말풍선, 카드                                 │
│ 복셀 디오라마 ← 공간 연결(scene) 규칙           │
└──────────────────┬────────────────────────────┘
                   │ RunAgentInput (메시지, 도구 정의, 공유 상태)
┌──────────────────▼────────────────────────────┐
│ 에이전트 (지금은 모의 에이전트)                   │
│   라우터 → 업무 영역별 처리기: 회의실 · 결재 · …   │
│   그룹웨어 백엔드 (지금은 가상 데이터 저장소)        │
└───────────────────────────────────────────────┘
```

- 화면은 **에이전트가 무엇을 띄울지 모른다.** 에이전트가 도구를 호출하면, 화면이 그 도구 이름에 맞는 카드를 카탈로그에서 찾아 그린다.
- 에이전트는 **화면을 모른다.** 도구 이름, 설명, 인자만 안다.
- 그래서 모의 에이전트를 실제 에이전트 서버로 바꿔도 화면 코드는 그대로 쓴다.

## AG-UI 이벤트

`src/agent/agui.ts`에 이 PoC가 쓰는 부분만 정의했다. 이름과 필드는 AG-UI 규격을 따른다. 실제 서버와 연결할 때는 공식 SDK(`@ag-ui/core`, `@ag-ui/client`) 타입으로 바꾼다.

| 이벤트 | 쓰임 |
|---|---|
| `RUN_STARTED` / `RUN_FINISHED` / `RUN_ERROR` | 실행 한 번의 시작·끝·오류 |
| `TEXT_MESSAGE_START` / `CONTENT` / `END` | 답변 글을 조금씩 보낸다. 말풍선 스트리밍 애니메이션의 입력 |
| `TOOL_CALL_START` / `ARGS` / `END` | 카드 띄우기. 인자가 스트리밍되는 동안에도 카드가 점진적으로 그려진다 |
| `STATE_SNAPSHOT` / `STATE_DELTA` | 공유 상태. DELTA는 JSON Patch(add·replace·remove) |

### 한 번의 왕복

1. 사용자가 입력 → `user` 메시지를 붙이고 실행한다.
2. 에이전트가 글을 스트리밍하고, 카드 도구를 호출한다.
3. 사용자가 카드에서 고른다 → 그 값이 `tool` 메시지(도구 결과)로 붙고 다시 실행한다. (**human-in-the-loop**)
4. 에이전트는 마지막 메시지가 무엇에 대한 도구 결과인지 보고 다음 카드를 띄우거나 일을 마친다.

새 요청이 오면 답을 기다리던 카드에는 `{"superseded":true}` 결과를 붙여 닫는다. 보여 주기만 하는 카드(완료 카드 등)는 실행이 끝날 때 화면이 `{"displayed":true}`로 응답한다.

## 업무 영역(도메인) 구조

업무마다 같은 모양의 묶음을 만든다.

```
src/agent/domains/<영역>/
  tools.ts      도구 이름, 인자·결과 타입, 도구 정의
  cards.tsx     도구 이름 → 카드 컴포넌트
  intent.ts     (모의) 요청 해석
  handler.ts    (모의) 사용자 메시지·도구 결과에 대한 처리
  scene.ts      (선택) 이 영역의 카드가 복셀에 무엇을 보여 줄지
  workspace.tsx (선택) 고정 작업 화면 (결재함 등)
  view.ts       (선택) 작업 화면의 보기 상태 (공유 상태에 들어감)
```

`src/agent/catalog.ts`가 모든 영역을 모아 **도구 정의 목록, 카드 카탈로그, 보여 주기만 하는 도구 목록**을 만든다. 새 업무를 붙일 때는 영역 폴더를 만들고 카탈로그에 한 줄 추가한다.

모의 에이전트(`src/agent/mock/agent.ts`)는 라우터다.
- 사용자 메시지: 각 영역 처리기의 `match()` 점수가 가장 높은 영역이 맡는다.
- 도구 결과: 그 도구를 가진 영역이 맡는다.

### 공유 상태

`AgentState`는 영역별 상태를 한 객체에 담는다. **업무 데이터 자체(결재 문서 목록 등)는 두지 않고**, "지금 무엇을 하고 있고 화면이 무엇을 보여 주는지"만 둔다. 업무 데이터는 화면과 에이전트가 같은 저장소(그룹웨어 API 자리)에서 읽는다.

```ts
interface AgentState {
  activeDomain: string | null;          // 처리 중인 업무 영역 → 레이아웃
  meetingRoom: { bookings: Booking[]; request: BookingRequest | null };
  approval: { view: ApprovalView };     // 결재함 화면의 탭·필터·선택 문서·의견 초안
}
```

공유 상태는 **양방향**이다. 에이전트는 `STATE_DELTA`로 바꾸고, 화면은 `useAgent().updateState`로 바꾼다. 화면이 바꾼 값은 다음 실행의 `RunAgentInput.state`로 에이전트에 간다.

## 고정 작업 화면과 대화 카드

| | 고정 작업 화면 (`DomainUI.workspace`) | 대화 카드 (`DomainUI.cards`) |
|---|---|---|
| 쓰는 곳 | 자주 쓰는 조회·처리 (결재함) | 대화에서 시작해 몇 단계로 끝나는 일 (기안, 회의실 예약) |
| 여는 방법 | 하단 바 바로가기 등으로 **에이전트 없이** 바로, 또는 에이전트가 공유 상태로 | 에이전트의 도구 호출 |
| 데이터 | 저장소를 직접 읽고 씀 | 에이전트가 인자로 넘김 |
| 에이전트 역할 | 화면 조작(필터·문서 열기), 요약, 의견 초안 | 흐름 진행 |

작업 화면이 열려 있으면 패널이 **왼쪽 작업 화면 + 오른쪽 대화 열(340px)** 로 나뉜다.

## 복셀 연동

각 영역은 `scene(call, args)`를 내보낼 수 있다. 답을 기다리는 가장 최근 카드에서 공간 정보를 뽑는다.

| 필드 | 뜻 |
|---|---|
| `candidates` | 고를 수 있는 회의실 (강조 + 3D에서 클릭 가능) |
| `active` | 지금 보고 있는 회의실 |
| `focus` | 카메라를 맞출 회의실 |
| `pickCallId` | 3D에서 방을 누르면 응답할 도구 호출 |
| `away` (선택) | 복셀에서 부재로 보여 줄 구성원 (휴가 신청한 날 미리보기) |
| `note` (선택) | 장면 위에 띄울 한 줄 안내 |

공간 정보가 없는 업무(결재 등)는 `scene`을 두지 않는다.

### 레이아웃 전환

에이전트는 처리할 업무 영역을 정하자마자 공유 상태 `activeDomain`을 바꾼다 (`STATE_DELTA`, 답변보다 먼저 온다). 화면은 그 영역이 공간 업무인지(`catalog.isSpatial`)로 레이아웃을 고른다. 기본은 `scene`을 가졌는지이고, 단계에 따라 달라지는 영역은 `DomainUI.spatial(state)`로 정한다 (일정 조율: 회의실을 고를 때만 복셀 중심).

| 경우 | 패널 | 복셀 |
|---|---|---|
| 공간 업무 (회의실) | 좁게 (360px) | 후보·선택한 방으로 확대, 패널 폭만큼 비켜서 초점 |
| 그 밖의 업무 (기안 등), 빈 패널, 도움말 | 넓게 (화면의 55%, 420~820px) | 사무실 전체를 남은 왼쪽 공간에 맞춰 줌 아웃 |
| 고정 작업 화면이 열림 (결재함) | 작업 화면 + 대화 열 (화면의 70%, 720~1180px) | 남은 왼쪽 공간에 줌 아웃 |

- 패널 폭은 CSS 변수(`--panel-w`)로 넘겨 0.35초 동안 부드럽게 바뀐다.
- 대화 영역은 container query 대상이라, 넓을 때 카드가 남는 폭을 쓴다 (결재 문서 2열, 시간 버튼 6열, 기안 폼 2열).
- 답변 말풍선은 넓은 패널에서도 560px을 넘지 않는다. 너비는 첫 단어를 내보내기 직전에 재서, 패널 폭이 바뀌는 중에도 줄바꿈이 어긋나지 않는다.

## 안전 원칙

- **되돌리기 어려운 동작은 항상 사람이 누른다.** 승인·반려·상신·예약은 카드의 버튼으로만 실행된다. 에이전트는 초안과 확인 카드까지만 만든다.
- 승인·반려는 카드 안에서 **한 번 더 확인**한다. 반려는 사유가 있어야 한다.
- **일괄 승인은 하지 않는다.** "다 승인해줘"라고 해도 문서를 하나씩 보여 준다.
- 카탈로그에 없는 도구를 호출하면 화면은 그리지 않고 안내만 한다.
- 카드는 인자가 **스트리밍 도중의 불완전한 값**일 때도 그려진다. 그래서 카드는 덜 채워진 인자를 견뎌야 하고, 그래도 깨지면 `CardBoundary`가 그 카드만 안내 문구로 바꿔 패널 전체가 멈추지 않게 한다. `src/agent/cards.test.tsx`가 모든 카드를 스트리밍 각 단계의 인자로 그려 보며 확인한다.
- 실제 연동 시 백엔드 도구는 **사용자 본인의 권한**으로 그룹웨어 API를 부르고, 실행 이력을 남긴다.
- 금지(D) 정보는 카드 입력란으로도 받지 않는다. ([groupware-tasks.md](groupware-tasks.md#다루지-않는-정보))

## 실제 에이전트로 바꿀 때

1. 에이전트 서버를 AG-UI로 띄운다 (예: Claude + LangGraph 또는 Pydantic AI). 서버는 화면이 보낸 `tools`를 프론트엔드 도구로 등록한다.
2. `DioramaWidget.tsx`의 `createMockAgent(...)`를 SSE로 이벤트를 받는 에이전트(공식 SDK의 HttpAgent 등)로 바꾼다.
3. 요청 해석(`intent.ts`)과 처리기(`handler.ts`)는 서버의 LLM과 백엔드 도구가 맡는다. 카드·카탈로그·복셀 연동은 그대로 쓴다.
4. IT 검토가 필요한 곳: 에이전트 서버의 외부 통신(LLM API), 그룹웨어 API 권한 범위, 대화·도구 결과 로그에 개인정보가 남는지, 저장 위치.
